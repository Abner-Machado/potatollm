# potatollm — foundation

Decision document. Written BEFORE the code. Whoever implements reads this first
and does not invent scope outside of it.

## 1. The question the tool answers

Just one:

> "Does this AI model run on my weak machine — and at what speed?"

Audience: whoever runs local LLMs on **CPU, no GPU, with little RAM**, on Windows.
It is not for those who have a video card. A tool already exists for those.

## 2. The problem is real (measured evidence, not conjecture)

Measured on 2026-08-20 on an i3-1215U machine, 7.7 GB of RAM, no GPU:

| model | result |
|---|---|
| qwen3-abliterated **8b** (5.0 GB) | **did not complete** 120 tokens in 10 minutes. Free RAM dropped to 0.07 GB, pagefile swelled to 9.5 GB |
| qwen3-abliterated **4b** (2.5 GB) | 7.48 tok/s, stable, 17s |

Ollama lets you download 5 GB to find this out on your own, afterwards. It does not warn before,
does not warn during, and the symptom (frozen machine) does not point at the cause.

## 3. Why it does not die like the competitors

Competitors verified on the GitHub API on 2026-08-20:

| repo | stars | focus |
|---|---|---|
| herczy/gguf-estimator | 0 | GGUF memory estimation |
| dlsniper/gguf-llm-vram-calculator | 2 | VRAM |
| GPUforLLM/llm-vram-calculator | 3 | VRAM |
| click6067-ship-it/fitllm-engine | 8 | "fit your GPU or Mac" |

All **estimate**, and all target **GPU/VRAM**. None covers CPU-only with short RAM.

Central decision: **the tool MEASURES, it does not estimate.**
A formula is copied in an afternoon. Accumulated data is not.
Estimation here is just triage; the product is the evidence.

## 4. The contradiction, and how it is resolved

Measuring requires downloading. The promise was to warn BEFORE downloading. Two-stage solution:

1. **check** — without downloading anything: reads the machine's real RAM and the model's size/quantization,
   classifies it as `fits comfortably` / `tight fit` / `will page` / `do not try`,
   and suggests the smallest equivalent when the verdict is bad.
2. **bench** — only after the user's OK: actually runs and measures.

Honest promise: *"I avoid the obviously bad download; when you decide to test, I actually measure."*

## 5. The vector is the TABLE, not the CLI

Nobody shares "I installed a CLI". What is shared is
"table of real tok/s of 15 models on an 8 GB machine without GPU".

- The README **opens with the table**, not with installation instructions.
- The repo **is born with data inside** (10 to 15 real measurements). An empty repo asking for
  contributions does not get contributions.
- Third-party contribution comes in via a Pull Request of one JSON file.

**Mandatory lock:** the JSON is ALWAYS generated by the CLI, with fixed schema and fixed prompt.
Never written by hand. Without this the table becomes an anecdote and loses the only thing that makes it
valuable: being comparable. Undetected field becomes explicit `"unknown"` — never a guess.

## 6. Installation — project constraint, not detail

The target user runs Ollama on Windows. **Ollama does not install Python nor Node.**
If installation asks for an environment, half give up before seeing value.

Hard rules:
- **Single file**, Python **3.9+**, **standard library only**. Zero external dependency.
- No virtualenv, no `requirements.txt`, no build step.
- Windows: a `.cmd` that runs with a double click.
- It has to work by downloading one file and running it.

## 7. v1 scope

**DOES:**
- `check <model>` — verdict without downloading
- `bench <model>` — measures real tok/s, free RAM at peak, pagefile at peak, whether it paged
- `selftest` — ping/diagnostic of its own chain (see section 8)
- writes JSON with fixed schema, generated only by the CLI
- `table` — converts the JSON into a Markdown table row

**DOES NOT in v1:**
answer quality, perplexity, GPU, multiple backends (Ollama only),
graphical interface, server, global ranking, automatic upload,
and does not accept hand-edited results as source for the table.

## 8. selftest (owner's requirement)

A command that proves the whole chain is alive, without relying on downloading a model:
- Python and version OK
- can read RAM/pagefile on this platform
- Ollama server responds (ping on the API) — and clearly says when it does NOT respond
- can write JSON and reconvert it into a table row
Readable output, and exit code 0 only if everything passed.

## 9. Test that proves v1 worked

Just one, verifiable: run `bench` against a small model, generate the JSON,
run `table`, and the table gains **exactly one new row derived from that JSON**,
without any manual editing.

## 11. How this was built

The tool was specified, written and reviewed by AI models under human direction,
and that process is documented here because it is part of what the numbers are worth.

- **Direction and final say:** the repo owner.
- **Architecture, review and verification:** Claude (Opus 5).
- **Implementation:** Hermes (gpt-5.5 via Codex), from a written brief.
- **English translation of this document:** DeepSeek V4 Flash.

The division mattered. The model that wrote the code reported "implemented and verified"
while shipping two fatal defects, both caught only by running the tool instead of reading it:

1. `selftest` printed `PASS ollama: Ollama responded` while the Ollama server was **switched
   off**. The version helper returned the string `"unknown"`, which is truthy in Python, so the
   failure branch never ran. A diagnostic tool that lies about a dead service is worse than none.
2. `check` returned the **same verdict** for the 4b and the 8b model — the two cases that
   justify the tool existing. It weighted instantaneous free RAM, which is volatile. The verdict
   now comes from total RAM, and free RAM is reported separately as a warning.

Seven more defects were found and fixed the same way. Nothing here was accepted because a
model said it worked; every claim in this repository was re-run and checked against the machine.
